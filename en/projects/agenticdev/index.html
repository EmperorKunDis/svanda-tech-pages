The problem

When developers each keep their own agent configuration and decisions remain inside separate chats, a team has difficulty tracing why work was done and how much access an agent had. AgenticDev explores a shared control plane for tasks, context, and run evidence.

Control plane

A FastAPI service tracks project, phase, and task context and prepares a work order for the agent run.

Scoped work order

The work order ties a task to a defined file scope, project rules, and phase. It is an input to runtime controls, not only a natural-language instruction.

Workspace and network

A launcher prepares a temporary container workspace. The repository is read-only by default, with selected writable paths; outbound traffic is intended to pass through an allowlisted proxy.

Run record and review

The host records run events and prepares a branch and review handoff. The model client performs the assigned task, while the surrounding platform governs context, access, and evidence.

Implementation status and limits

The project is a public alpha. Runtime isolation exists in code, but adversarial acceptance on a clean VPS remains open. Forgejo protections, runner, and merge gate are prepared; actual merge blocking on a live Forgejo service has not been demonstrated. A successful local check does not qualify the whole deployment as safe for autonomous production work.

Why these boundaries matter

The platform treats the model as one participant in a controlled engineering process. Scope checks, tests, and human review help reviewers assess a proposed change. They do not replace the team's own security review or acceptance of a deployment.
