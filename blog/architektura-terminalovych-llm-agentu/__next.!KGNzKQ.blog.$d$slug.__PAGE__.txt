35:Tdc88,<p><strong>Samotný model je jen jedna komponenta. Spolehlivost vzniká v systému kolem něj.</strong></p>
<p>V Prautu používáme vlastní variantu <strong>Pi harnessu</strong>. Harness chápu jako prostředí, které propojuje model s kontextem, nástroji, životním cyklem úkolu a pravidly skutečné exekuce. Právě návrh tohoto celku rozhoduje, zda se z působivé odpovědi stane použitelný výsledek.</p>
<p>Tento text popisuje moje architektonické východisko pro agentní systémy a aplikace s integrovanými LLM. Pi je náš pracovní základ; Claude Code, Codex CLI, Gemini CLI a další nástroje jsou užitečné srovnávací implementace. Jejich funkce ani níže uvedená referenční architektura nejsou automaticky seznamem vlastností každého projektu v portfoliu. U konkrétních studií uvádím, co je implementované, co je prototyp a co ještě čeká na ověření.</p>
<p><em>Technický přehled k 5. říjnu 2026. Ukázky označené jako pseudokód popisují návrhový kontrakt, nikoli hotovou bezpečnostní implementaci nebo přenositelné API všech frameworků.</em></p>
<h2 id="exekutivni-shrnuti">Exekutivní shrnutí</h2>
<p>Kvalitní terminálový agent propojuje několik vrstev: sestavení kontextu, model, řízení úkolu, typované nástroje, politiku oprávnění, stav a paměť, izolované prostředí, průběžné události a měření výsledků. Kolem těchto vrstev se sbližují různé implementace, přestože používají odlišné názvy a API.</p>
<p><strong>První princip: model navrhuje, runtime rozhoduje o provedení.</strong> Lifecycle hooky a middleware umožňují vstup upravit, tool call ověřit, výsledek normalizovat a průběh zaznamenat. Skutečné oprávnění musí vycházet z důvěryhodné konfigurace a být vynucené i mimo generativní model.</p>
<p><strong>Druhý princip: přenositelnost potřebuje jasnou nástrojovou hranici.</strong> MCP standardizuje propojení hosta, klientů a serverů, včetně nástrojů, zdrojů a promptů nad JSON-RPC. Referencí tohoto přehledu je specifikace 2026-07-28. Vedle MCP zůstávají relevantní lokální funkce a nativní tool-calling API. Protokol sám nevynucuje bezpečnostní politiku aplikace. <a href="https://modelcontextprotocol.io/specification/2026-07-28">Specifikace MCP</a></p>
<p><strong>Třetí princip: složitost si musí zasloužit místo.</strong> Začínám jedním agentem a dobře navrženými nástroji. Router, plánovač nebo tým specialistů přidává smysl tehdy, když prokazatelně zlepší výsledek nebo čas dokončení. Další agent současně znamená další kontext, rozhodnutí a možnost chyby. Stejné východisko doporučuje dokumentace <a href="https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html">AutoGen Teams</a>.</p>
<p><strong>Čtvrtý princip: stav a paměť mají rozdílné odpovědnosti.</strong> Stav určuje, kde běh skončil a co už provedl. Paměť uchovává znalosti použitelné později. Checkpoint není náhrada dlouhodobé paměti a uložená konverzace sama nezaručuje bezpečné pokračování po pádu. <a href="https://docs.langchain.com/oss/python/langgraph/persistence">LangGraph Persistence</a></p>
<p><strong>Pátý princip: prompt není bezpečnostní hranice.</strong> Model může chybně interpretovat web, README i odpověď nástroje. Oprávnění, izolace, kontrola síťových spojení a schválení významných akcí patří do exekuční vrstvy. Bezpečnostní rozbor musí pokrýt také paměť, dodavatelský řetězec rozšíření a opakované vedlejší účinky. <a href="https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/">OWASP Agentic Top 10</a></p>
<p><strong>Šestý princip: zlepšování se měří.</strong> Změna modelu, promptu, nástroje nebo orchestrace se porovnává s regresním datasetem a explicitními kritérii úspěchu. Tracing vysvětluje průběh; evaluace hodnotí výsledek. Potřebujeme obojí.</p>
<h2 id="referencni-architektura-a-odpovednosti-vrstev">Referenční architektura a odpovědnosti vrstev</h2>
<p><img src="/media/blog/editorial/agent-runtime.svg" alt="Referenční agentní runtime: kontext a model navrhují akci, policy gateway ji ověří před izolovaným nástrojem; stav, paměť a telemetrie mají vlastní odpovědnosti." /></p>
<p>Uživatel zadá úkol. Pre-input hook provede kontrolu vstupu a context builder načte relevantní projektová pravidla, stav a doloženou paměť. Agent nebo orchestrátor přes modelový adaptér získá odpověď či návrh nástroje. Před každou skutečnou akcí následuje validace argumentů a kontrola oprávnění. Teprve schválený požadavek smí přejít do nástrojového adaptéru a izolovaného prostředí.</p>
<p>Výsledek nástroje se vrací přes post-tool zpracování do agentního cyklu. Stav se ukládá po významných přechodech. Výstup pro uživatele prochází vlastní validací. Streaming událostí průběžně informuje terminál a korelovaná telemetrie umožňuje celý běh rekonstruovat. Zamítnutá akce se zaznamená a vrátí jako řízený výsledek, nikoli jako pokyn obejít kontrolu jinou cestou.</p>

<p>Hook je obvykle callback konkrétní události. Middleware obaluje další výpočet a může řídit pokračování. LangChain nabízí oba styly; Semantic Kernel používá také pojem filter a pokračovací callback. Rozhodující je smlouva: kdy se kód volá, jaké informace obdrží, co smí změnit a co se stane při chybě. <a href="https://docs.langchain.com/oss/python/langchain/middleware/custom">LangChain Custom Middleware</a>, <a href="https://learn.microsoft.com/en-us/semantic-kernel/concepts/enterprise-readiness/filters">Semantic Kernel Filters</a></p>
<p>Následující pseudokód odděluje kontrolní body:</p>
<pre><code class="language-python">async def run_tool(call, identity, runtime):
    validated = runtime.schemas.validate(call)
    decision = runtime.policy.evaluate(identity, validated)
    runtime.audit.record_decision(call.id, decision)

    if not decision.allowed:
        raise ToolDenied(decision.reason)

    if decision.requires_approval:
        approval = await runtime.approvals.request(validated)
        runtime.approvals.verify_exact_action(approval, validated)

    # Runner znovu vynutí scope i při přímém volání adaptéru.
    result = await runtime.runner.execute(validated, decision.capabilities)
    runtime.audit.record_result(call.id, result.status)
    return runtime.outputs.normalize_untrusted(result)
</code></pre>
<p>Samotná normalizace textu neodstraňuje prompt injection. Vrácený obsah stále nese původ a důvěryhodnost; nesmí se proměnit v autoritativní instrukci. Stejně tak nepředpokládám, že všechny hosty při chybě hooku zastaví akci. Například dokumentace Codexu rozlišuje podporované blokovací výstupy a nepodporovaná pole, u nichž může volání pokračovat. <a href="https://learn.chatgpt.com/docs/hooks">Codex Hooks</a></p>
<h3 id="streaming-potrebuje-vlastni-datovy-model">Streaming potřebuje vlastní datový model</h3>
<p>Terminál potřebuje vědět nejen to, jaký text právě vzniká, ale i to, zda se načítá kontext, čeká na schválení nebo běží nástroj. Textové delty a lifecycle události proto odděluji.</p>
<pre><code class="language-python"># Ilustrační event loop; názvy událostí jsou interní kontrakt aplikace.
async for event in agent.stream():
    match event.type:
        case "text.delta":
            terminal.write(event.delta)
        case "tool.args.delta":
            buffers[event.call_id].append(event.delta)
        case "tool.ready":
            call = parse_complete_call(buffers.pop(event.call_id))
            await run_tool(call, identity, runtime)
        case "tool.started":
            terminal.show_running(event.call_id)
        case "tool.finished":
            terminal.show_result(event.call_id, event.status)
        case "usage":
            metrics.record_usage(event)
        case "error":
            terminal.show_error(event.safe_message)
</code></pre>
<p>Argumenty mohou přijít po neúplných částech. Nástroj se nespouští na prvním fragmentu: čeká se na dokončení, schema validation a policy rozhodnutí. Implementace potřebuje také limity bufferů, backpressure, zrušení a korelaci událostí po reconnectu. Fine-grained tool streaming výslovně upozorňuje na neúplný JSON. <a href="https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming">Anthropic: tool streaming</a></p>
<h3 id="mcp-a-lokalni-function-calling">MCP a lokální function calling</h3>
<p>Lokální tool je vhodný pro schopnost úzce spojenou s aplikací. MCP dává smysl tam, kde stejnou schopnost potřebuje více hostů nebo je vhodné oddělit její správu. V obou případech potřebuji identitu volajícího, validované argumenty, pravidla přístupu a strukturovaný výsledek.</p>
<pre><code class="language-json">{
  "name": "workspace.read_text",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": { "type": "string" },
      "max_bytes": { "type": "integer", "minimum": 1, "maximum": 100000 }
    },
    "required": ["path"],
    "additionalProperties": false
  }
}
</code></pre>
<p>Toto je příklad interního schématu, nikoli univerzální registrační payload. Runner musí navíc vyřešit kořen workspace, symlinky, souběžné změny cest a oprávnění skutečně otevřeného souboru. Validní JSON ještě neznamená povolenou operaci.</p>
<p>Ukázka běžného hostitelského konfiguračního tvaru pro lokální MCP server:</p>
<pre><code class="language-json">{
  "mcpServers": {
    "project-tools": {
      "command": "python",
      "args": ["-m", "project_mcp"],
      "env": { "PROJECT_ROOT": "/workspace" }
    }
  }
}
</code></pre>
<p>Název konfiguračního klíče a způsob spuštění určuje host, ne samotný protokol. <code>PROJECT_ROOT</code> je konvence této ukázky. Tajné klíče do sdílené konfigurace nepatří. MCP zlepšuje interoperabilitu; autorizace a izolace zůstávají odpovědností konkrétní implementace.</p>

<h2 id="stav-checkpointy-a-bezpecne-pokracovani">Stav, checkpointy a bezpečné pokračování</h2>
<p>Stav běhu potřebuje více než historii zpráv:</p>
<pre><code class="language-python">from dataclasses import dataclass, field
from typing import Literal

@dataclass
class RunState:
    task_id: str
    phase: Literal["plan", "edit", "test", "review", "blocked", "done"]
    workspace_revision: str
    completed_steps: list[str] = field(default_factory=list)
    operation_ids: list[str] = field(default_factory=list)
    pending_approval_id: str | None = None
</code></pre>
<p>Checkpoint se ukládá po významném přechodu spolu s verzí kontextu a konfigurace. Při obnově se nejdříve ověří skutečný stav prostředí. Změnil se repozitář? Vypršelo oprávnění? Dokončil externí systém operaci, jejíž odpověď se ztratila?</p>
<p>Nejnebezpečnější okno je mezi provedením vedlejšího účinku a uložením jeho výsledku. Pouhé <code>checkpoint.commit()</code> po volání API toto okno neřeší. Potřebujeme idempotency klíč, transakční outbox nebo reconciliaci s cílovým systémem podle jeho možností.</p>
<pre><code class="language-text">Zapsat záměr a operation_id
→ ověřit oprávnění a případný souhlas
→ provést operaci s idempotency klíčem
→ uložit potvrzený výsledek
→ posunout checkpoint

Po pádu: nejdřív zjistit stav operation_id, potom rozhodnout o opakování.
</code></pre>
<p>Pro čtení může být retry levný a bezpečný. U odeslání e-mailu, vytvoření objednávky nebo publikace změny by slepé opakování mohlo znamenat druhou skutečnou akci. Ani obnovení lokálního filesystemu nevrací automaticky zpět změny v externím systému.</p>

<pre><code class="language-python"># Pseudokód: interní názvy spanů, nikoli závazná OTel schema.
with trace.span("agent.turn", task_id=task_id, session_id=session_id):

    for call in response.tool_calls:

</code></pre>
<p>Prompty a výsledky nástrojů mohou obsahovat osobní údaje i secrets. Výchozí telemetrie proto zaznamenává bezpečné atributy, stav, čas a korelaci; obsah má vlastní pravidla redakce, přístupu a retence. Trace ID nepoužívám jako metriku s neomezenou kardinalitou.</p>
<p>OpenTelemetry rozvíjí GenAI konvence a jejich dokumentace se přesunula do samostatného repozitáře. Stabilitu je nutné kontrolovat u konkrétních atributů a verzí. <h2 id="sandboxing-a-bezpecnost-nastrojoveho-runtime">Sandboxing a bezpečnost nástrojového runtime</h2>
<p>Runner má fungovat jako prostředník přidělující konkrétní schopnosti. Modelový návrh shell příkazu není sám o sobě oprávněním k jeho provedení.</p>
<pre><code class="language-yaml"># Ilustrační politika; musí ji vynucovat runner a systémové mechanismy.
workspace: /repo
filesystem:
  read_only: [/repo]
  writable: [/repo/src, /repo/tests]
  deny: [/repo/.env]
network:
  default: deny
  allow_hosts: [registry.npmjs.org, pypi.org]
limits:
  runtime_seconds: 120
  processes: 32
approvals:
  required_for: [deploy, git.push, database.delete, email.send]
</code></pre>
<p>Allowlist domén není úplná síťová ochrana. Záleží na DNS, proxy, přesměrování, dostupných protokolech i tom, jaká data může nástroj odeslat na povolenou službu. Mounty, credentials, CPU, paměť a procesy mají vlastní omezení. Citlivé soubory hostitele se do prostředí vůbec nemusí dostat.</p>
<p>Schválení musí být navázané na konkrétní payload nebo diff, identitu a platnost. Změní-li se akce po schválení, původní souhlas nestačí. Agent také nemá mít možnost přepsat policy či testovací bránu, podle které se jeho práce posuzuje.</p>
<h3 id="minimalni-threat-model">Minimální threat model</h3>
<ol>
<li><strong>Prompt injection:</strong> externí dokument, web, issue nebo výsledek nástroje se snaží přepsat zadání. Odděluji data od autority a kontroluji skutečné akce.</li>
<li><strong>Excessive agency:</strong> nástroj má větší rozsah, než úloha vyžaduje. Omezuji schopnosti a dobu jejich platnosti.</li>
<li><strong>Tool/MCP poisoning:</strong> změna popisu, implementace či odpovědi nástroje ovlivní rozhodování. Verzuji a prověřuji dodavatele i kontrakty.</li>
<li><strong>Memory poisoning:</strong> nedůvěryhodný obsah přežije v paměti do další session. Uchovávám provenance a řídím zápis i retrieval.</li>
<li><strong>Improper output handling:</strong> aplikace použije vygenerovaný shell, SQL, HTML nebo URL bez běžné validace. Výstup modelu zůstává nedůvěryhodným vstupem.</li>
<li><strong>Supply-chain útoky:</strong> skill, plugin nebo extension přináší kód a nové možnosti exekuce. Připínám verze, kontroluji zdroj a oprávnění.</li>
<li><strong>Selhání obnovy a souběhu:</strong> dva běhy provedou stejnou akci nebo pracují s jinou revizí. Používám operation IDs, zámky či transakce podle domény.</li>
</ol>
<p>Pro mapování rizik používám <a href="https://genai.owasp.org/llm-top-10/">OWASP LLM Top 10</a>, <a href="https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/">OWASP Agentic Top 10</a> a <a href="https://atlas.mitre.org/">MITRE ATLAS</a>. Tyto zdroje jsou rámec pro threat modeling, nikoli certifikát bezpečnosti konkrétní aplikace.</p>
<p>Bezpečnostní test musí zkoušet i chybu policy služby, timeout hooku, podvržený tool result a pokus změnit konfiguraci během běhu. U bezpečnostně kritického rozhodnutí má nedostupná kontrola zabránit provedení, nikoli otevřít alternativní cestu.</p>
<h2 id="ci-cd-a-verzovani-celeho-agentniho-systemu">CI/CD a verzování celého agentního systému</h2>
<p>Nasazení agenta mění více než zdrojový kód aplikace. Model, instrukce, nástroje, paměť a runtime konfigurace společně určují chování.</p>
<pre><code class="language-yaml"># Logická pipeline; není to přímo spustitelný GitHub Actions workflow.
pull_request:
  - lint_and_unit_tests
  - tool_contract_tests
  - deterministic_agent_smoke_evals
  - prompt_regressions
  - policy_and_sandbox_tests
merge_to_main:
  - full_agent_eval
  - security_red_team
  - build_versioned_bundle
  - deploy_canary
canary:
  - compare_task_success
  - compare_latency_and_cost
  - inspect_policy_denials
  - rollback_on_regression
nightly:
  - larger_eval_suite
  - dependency_and_plugin_scan
  - adversarial_cases
  - redacted_production_trace_sampling
</code></pre>
<p>Do verze artefaktu zahrnuji identifikátor modelu a routing, system prompty, projektová pravidla, skills, tool schemas, MCP servery, policy, eval dataset, paměťové schema a digest sandbox image. Když se po releasu změní chování, potřebujeme najít konkrétní rozdíl.</p>
<p>Canary porovnává kvalitu i provozní náklady. Vyšší počet policy denials může znamenat lepší ochranu, ale také chybné blokování běžné práce. Metriky vyhodnocuji společně a v kontextu typu úlohy. Rollback musí počítat s kompatibilitou uloženého stavu; návrat starého kódu nemusí automaticky vrátit schema paměti nebo změny provedené venku.</p>
<h2 id="performance-tuning-podle-navratnosti">Performance tuning podle návratnosti</h2>
<p>Nejdříve změřím, kde vzniká čekání a kolik stojí úspěšné dokončení. Pak volím konkrétní zásah:</p>
<ol>
<li><strong>Stabilní prompt prefix:</strong> využít opakované části kontextu tam, kde to provider podporuje.</li>
<li><strong>Context pruning:</strong> nahradit přebytečný historický log strukturovaným stavem a relevantními podklady.</li>
<li><strong>Progressive tool disclosure:</strong> zpřístupnit aktuálně potřebnou sadu schopností místo stovek schémat.</li>
<li><strong>Paralelizace nezávislých čtení:</strong> repozitář, dokumentaci a issue lze často načíst souběžně. Zápisy do sdíleného stavu vyžadují jiný návrh.</li>
<li><strong>Streaming:</strong> zkrátit čekání na první užitečnou informaci, i když se celkový compute nezmění.</li>
<li><strong>Model routing:</strong> jednoduchou klasifikaci přenechat menšímu modelu, složitou syntézu silnějšímu; routing samostatně evaluovat.</li>
<li><strong>Rozpočty a stop podmínky:</strong> zabránit nekonečným smyčkám a opakování stejné chyby.</li>
</ol>
<pre><code class="language-python"># Ilustrační limity pro jednu třídu úloh, nikoli univerzální doporučení.
budgets = {
    "max_turns": 40,
    "max_tool_calls": 100,
    "max_same_tool_retries": 3,
    "max_tokens": 100_000,
    "wall_clock_timeout_seconds": 900,
    "max_cost_usd": 2.0,
}
</code></pre>
<p>Po dosažení limitu systém uloží stav, sdělí dosažený výsledek a konkrétní překážku. Neoznačí úkol za hotový jen proto, že už nemá rozpočet.</p>
<p>LLMCompiler ukazuje význam plánování závislostí a paralelního vykonávání nezávislých tool callů. Výsledky konkrétního benchmarku však nepřenáším na vlastní produkt bez měření. <a href="https://arxiv.org/abs/2312.04511">LLMCompiler</a></p>

<p>ReAct pomáhá popsat cyklus rozhodnutí, akce a pozorování. MRKL specializaci a routing. Self-Refine a Reflexion práci se zpětnou vazbou. Tree of Thoughts rozšiřuje hledání na více kandidátních cest. Každý pattern má cenu v inferencích, stavu a testování. Výzkumný přínos není důvod použít všechny vzory současně.</p>
<p>Praktické diskuse přidávají opakující se problémy: stale state, runaway retry loops, duplicitní vedlejší účinky, rozpadající se streaming a chybějící tool ledger. Fórum může být podnětem k testu. Autoritativní kontrakt API hledám v dokumentaci a konkrétní chování ověřuji v připnuté verzi.</p>
<p>Český kontext má stejnou technickou podstatu: firemní data, interní procesy, oprávnění a omezená kapacita na provoz. U databázového asistenta například často dává smysl úzce vymezený read-only nástroj bez předání dlouhodobého hesla modelu. U hlasové recepce je zásadní návaznost hovoru na stav úlohy a ověřitelný záznam. U vývojového agenta scope změny, testy a předání výsledku. Lokální jazyk ani lokální model tyto odpovědnosti neodstraňují.</p>
<h2 id="jak-se-tento-pristup-promita-do-me-prace">Jak se tento přístup promítá do mé práce</h2>
<p>V <a href="/projekty/agenticdev">AgenticDev</a> je těžištěm řízení kontextu, pracovního běhu a auditní stopy. <a href="/projekty/posthub">PostHub</a> spojuje kontext jednotlivých značek s asynchronním zpracováním a schvalováním. <a href="/projekty/zaznamnik-pro">Zaznamnik.pro</a> propojuje hlasovou interakci s navazujícím backendovým procesem. Každá studie popisuje konkrétní stav a jeho omezení.</p>
<p>Stejný systémový pohled se uplatňuje i mimo LLM: u <a href="/projekty/sch-ekonom-klientsky-portal">SCH-EKONOM</a> na rolích a návaznosti pracovních toků, u <a href="/projekty/ept-connectors-recepce">EPT recepce</a> na cestě od OCR přes potvrzení údajů k evidenci návštěvy. Ne každý problém potřebuje generativní model. Každý potřebuje jasné odpovědnosti, správná data a kontrolovatelný výsledek.</p>
<p><strong>LLM patří dovnitř explicitně stavového runtime s řízenými pravomocemi.</strong> Umí navrhnout další krok; systém kolem něj musí zajistit, že je krok přípustný, dohledatelný a vyhodnotitelný. To je pro mě podstata ucelené architektury agentních a LLM systémů.</p>
