Model je jedna komponenta. Ucelený agentní systém propojuje kontext, nástroje, stav, paměť, oprávnění, izolovanou exekuci a evaluace. Architektonický průvodce z pohledu Prautu a vlastní varianty Pi harnessu.

Samotný model je jen jedna komponenta. Spolehlivost vzniká v systému kolem něj.

V Prautu používáme vlastní variantu Pi harnessu. Harness chápu jako prostředí, které propojuje model s kontextem, nástroji, životním cyklem úkolu a pravidly skutečné exekuce. Právě návrh tohoto celku rozhoduje, zda se z působivé odpovědi stane použitelný výsledek.

Exekutivní shrnutí

Kvalitní terminálový agent propojuje několik vrstev: sestavení kontextu, model, řízení úkolu, typované nástroje, politiku oprávnění, stav a paměť, izolované prostředí, průběžné události a měření výsledků. Kolem těchto vrstev se sbližují různé implementace, přestože používají odlišné názvy a API.

První princip: model navrhuje, runtime rozhoduje o provedení. Lifecycle hooky a middleware umožňují vstup upravit, tool call ověřit, výsledek normalizovat a průběh zaznamenat. Skutečné oprávnění musí vycházet z důvěryhodné konfigurace a být vynucené i mimo generativní model.

Druhý princip: přenositelnost potřebuje jasnou nástrojovou hranici. MCP standardizuje propojení hosta, klientů a serverů, včetně nástrojů, zdrojů a promptů nad JSON-RPC. Referencí tohoto přehledu je specifikace 2026-07-28. Vedle MCP zůstávají relevantní lokální funkce a nativní tool-calling API. Protokol sám nevynucuje bezpečnostní politiku aplikace. Specifikace MCP

Třetí princip: složitost si musí zasloužit místo. Začínám jedním agentem a dobře navrženými nástroji. Router, plánovač nebo tým specialistů přidává smysl tehdy, když prokazatelně zlepší výsledek nebo čas dokončení. Další agent současně znamená další kontext, rozhodnutí a možnost chyby. Stejné východisko doporučuje dokumentace AutoGen Teams.

Čtvrtý princip: stav a paměť mají rozdílné odpovědnosti. Stav určuje, kde běh skončil a co už provedl. Paměť uchovává znalosti použitelné později. Checkpoint není náhrada dlouhodobé paměti a uložená konverzace sama nezaručuje bezpečné pokračování po pádu. LangGraph Persistence

Pátý princip: prompt není bezpečnostní hranice. Model může chybně interpretovat web, README i odpověď nástroje. Oprávnění, izolace, kontrola síťových spojení a schválení významných akcí patří do exekuční vrstvy. Bezpečnostní rozbor musí pokrýt také paměť, dodavatelský řetězec rozšíření a opakované vedlejší účinky. OWASP Agentic Top 10

Šestý princip: zlepšování se měří. Změna modelu, promptu, nástroje nebo orchestrace se porovnává s regresním datasetem a explicitními kritérii úspěchu. Tracing vysvětluje průběh; evaluace hodnotí výsledek. Potřebujeme obojí.

Referenční architektura a odpovědnosti vrstev

Uživatel zadá úkol. Pre-input hook provede kontrolu vstupu a context builder načte relevantní projektová pravidla, stav a doloženou paměť. Agent nebo orchestrátor přes modelový adaptér získá odpověď či návrh nástroje. Před každou skutečnou akcí následuje validace argumentů a kontrola oprávnění. Teprve schválený požadavek smí přejít do nástrojového adaptéru a izolovaného prostředí.

Výsledek nástroje se vrací přes post-tool zpracování do agentního cyklu. Stav se ukládá po významných přechodech. Výstup pro uživatele prochází vlastní validací. Streaming událostí průběžně informuje terminál a korelovaná telemetrie umožňuje celý běh rekonstruovat. Zamítnutá akce se zaznamená a vrátí jako řízený výsledek, nikoli jako pokyn obejít kontrolu jinou cestou.

Hook je obvykle callback konkrétní události. Middleware obaluje další výpočet a může řídit pokračování. LangChain nabízí oba styly; Semantic Kernel používá také pojem filter a pokračovací callback. Rozhodující je smlouva: kdy se kód volá, jaké informace obdrží, co smí změnit a co se stane při chybě. LangChain Custom Middleware, Semantic Kernel Filters

Následující pseudokód odděluje kontrolní body:

async def run_tool(call, identity, runtime):
    validated = runtime.schemas.validate(call)
    decision = runtime.policy.evaluate(identity, validated)
    runtime.audit.record_decision(call.id, decision)

    if not decision.allowed:
        raise ToolDenied(decision.reason)

    if decision.requires_approval:
        approval = await runtime.approvals.request(validated)
        runtime.approvals.verify_exact_action(approval, validated)

    # Runner znovu vynutí scope i při přímém volání adaptéru.
    result = await runtime.runner.execute(validated, decision.capabilities)
    runtime.audit.record_result(call.id, result.status)
    return runtime.outputs.normalize_untrusted(result)

Samotná normalizace textu neodstraňuje prompt injection. Vrácený obsah stále nese původ a důvěryhodnost; nesmí se proměnit v autoritativní instrukci. Stejně tak nepředpokládám, že všechny hosty při chybě hooku zastaví akci. Například dokumentace Codexu rozlišuje podporované blokovací výstupy a nepodporovaná pole, u nichž může volání pokračovat. Streaming potřebuje vlastní datový model

Terminál potřebuje vědět nejen to, jaký text právě vzniká, ale i to, zda se načítá kontext, čeká na schválení nebo běží nástroj. Textové delty a lifecycle události proto odděluji.

# Ilustrační event loop; názvy událostí jsou interní kontrakt aplikace.
async for event in agent.stream():
    match event.type:
        case "text.delta":
            terminal.write(event.delta)
        case "tool.args.delta":
            buffers[event.call_id].append(event.delta)
        case "tool.ready":
            call = parse_complete_call(buffers.pop(event.call_id))
            await run_tool(call, identity, runtime)
        case "tool.started":
            terminal.show_running(event.call_id)
        case "tool.finished":
            terminal.show_result(event.call_id, event.status)
        case "usage":
            metrics.record_usage(event)
        case "error":
            terminal.show_error(event.safe_message)

Argumenty mohou přijít po neúplných částech. Nástroj se nespouští na prvním fragmentu: čeká se na dokončení, schema validation a policy rozhodnutí. Implementace potřebuje také limity bufferů, backpressure, zrušení a korelaci událostí po reconnectu. Fine-grained tool streaming výslovně upozorňuje na neúplný JSON. Anthropic: tool streaming

MCP a lokální function calling

Lokální tool je vhodný pro schopnost úzce spojenou s aplikací. MCP dává smysl tam, kde stejnou schopnost potřebuje více hostů nebo je vhodné oddělit její správu. V obou případech potřebuji identitu volajícího, validované argumenty, pravidla přístupu a strukturovaný výsledek.

{
  "name": "workspace.read_text",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": { "type": "string" },
      "max_bytes": { "type": "integer", "minimum": 1, "maximum": 100000 }
    },
    "required": ["path"],
    "additionalProperties": false
  }
}

Toto je příklad interního schématu, nikoli univerzální registrační payload. Runner musí navíc vyřešit kořen workspace, symlinky, souběžné změny cest a oprávnění skutečně otevřeného souboru. Validní JSON ještě neznamená povolenou operaci.

Ukázka běžného hostitelského konfiguračního tvaru pro lokální MCP server:

{
  "mcpServers": {
    "project-tools": {
      "command": "python",
      "args": ["-m", "project_mcp"],
      "env": { "PROJECT_ROOT": "/workspace" }
    }
  }
}

Název konfiguračního klíče a způsob spuštění určuje host, ne samotný protokol. PROJECT_ROOT je konvence této ukázky. Tajné klíče do sdílené konfigurace nepatří. MCP zlepšuje interoperabilitu; autorizace a izolace zůstávají odpovědností konkrétní implementace.

Pro coding agenta je často dostačující hlavní agent, výzkumný nástroj a deterministická smyčka kontroly změn. Náročnější úkol přejde k plánovači; nezávislé části se rozdělí, výsledky se sloučí a následují testy, kontrola diffu a případná lidská brána.

Úkol → hlavní agent → změna → testy a lint → kontrola diffu → výsledek
          │                       │                │
          ├─ výzkum jako tool      └─ chyba → oprava └─ riziková akce → souhlas
          └─ plán → nezávislé podúlohy → spojení výsledků

Handoff předává řízení; agent-as-tool vrací dílčí výsledek původnímu volajícímu. Volba ovlivňuje historii, autoritu, rozpočty i to, kdo má rozhodnout o ukončení. Rozdíl je popsaný také v OpenAI Agents SDK: orchestration.

Přínos multi-agent řešení posuzuji proti stejným úlohám a stejným kritériím jako jednoduchý baseline. Měřím úspěšnost, čas, cenu za dokončený úkol a počet nových failure modes. Počet agentů sám o sobě není ukazatel kvality.

Stav, checkpointy a bezpečné pokračování

Stav běhu potřebuje více než historii zpráv:

from dataclasses import dataclass, field
from typing import Literal

@dataclass
class RunState:
    task_id: str
    phase: Literal["plan", "edit", "test", "review", "blocked", "done"]
    workspace_revision: str
    completed_steps: list[str] = field(default_factory=list)
    operation_ids: list[str] = field(default_factory=list)
    pending_approval_id: str | None = None

Checkpoint se ukládá po významném přechodu spolu s verzí kontextu a konfigurace. Při obnově se nejdříve ověří skutečný stav prostředí. Změnil se repozitář? Vypršelo oprávnění? Dokončil externí systém operaci, jejíž odpověď se ztratila?

Nejnebezpečnější okno je mezi provedením vedlejšího účinku a uložením jeho výsledku. Pouhé checkpoint.commit() po volání API toto okno neřeší. Potřebujeme idempotency klíč, transakční outbox nebo reconciliaci s cílovým systémem podle jeho možností.

Zapsat záměr a operation_id
→ ověřit oprávnění a případný souhlas
→ provést operaci s idempotency klíčem
→ uložit potvrzený výsledek
→ posunout checkpoint

Po pádu: nejdřív zjistit stav operation_id, potom rozhodnout o opakování.

Pro čtení může být retry levný a bezpečný. U odeslání e-mailu, vytvoření objednávky nebo publikace změny by slepé opakování mohlo znamenat druhou skutečnou akci. Ani obnovení lokálního filesystemu nevrací automaticky zpět změny v externím systému.

Paměť s původem, platností a hranicemi důvěry

Paměť má vlastní životní cyklus: vznik, zdroj, ověření, zpřístupnění, aktualizaci a smazání. Uložený text není automaticky pravdivý ani autoritativní.

Prompt engineering a context engineering

Dobrý prompt zasazuji do životního cyklu systému. Důležité je, kdo instrukci vydal, jak dlouho platí, kolik kontextu spotřebuje a zda přináší měřitelný přínos.

Context engineering zahrnuje výběr, pořadí, rozpočty, provenance a obnovování informací. Do každého kroku neposílám celý archiv ani všechny dostupné nástroje. Zpřístupňuji relevantní schopnosti postupně a při compaction zachovávám zadání, omezení, stav operací a nevyřešené otázky.

Historické instrukce mají projít stejným měřením jako nový prompt. Pokud odstranění části scaffoldu nezhorší výsledek a zlepší latenci, je to užitečná změna. Pokud jej zhorší, potřebujeme vědět na jakých úlohách. Rozhoduje regresní srovnání, nikoli délka system promptu.

LLM judge je vhodný tam, kde výsledek vyžaduje posouzení nuance. Pokud existuje deterministická pravda — exit code, schema, test, diff policy, počet řádků nebo hash — použiji běžný program. Judge potřebuji kalibrovat proti lidskému hodnocení a sledovat jeho vlastní bias.

Doporučený event model

# Pseudokód: interní názvy spanů, nikoli závazná OTel schema.
with trace.span("agent.turn", task_id=task_id, session_id=session_id):
    with trace.span("model.call", model=model_version):
        response = await model.generate(context)

    for call in response.tool_calls:
        with trace.span("tool.call", tool=call.name, call_id=call.id):
            result = await run_tool(call, identity, runtime)
            metrics.record_status(call.name, result.status)

Prompty a výsledky nástrojů mohou obsahovat osobní údaje i secrets. Výchozí telemetrie proto zaznamenává bezpečné atributy, stav, čas a korelaci; obsah má vlastní pravidla redakce, přístupu a retence. Trace ID nepoužívám jako metriku s neomezenou kardinalitou.

OpenTelemetry rozvíjí GenAI konvence a jejich dokumentace se přesunula do samostatného repozitáře. Stabilitu je nutné kontrolovat u konkrétních atributů a verzí. Interní event model proto odděluji od exportního adaptéru. OpenTelemetry GenAI

Sandboxing a bezpečnost nástrojového runtime

Runner má fungovat jako prostředník přidělující konkrétní schopnosti. Modelový návrh shell příkazu není sám o sobě oprávněním k jeho provedení.

# Ilustrační politika; musí ji vynucovat runner a systémové mechanismy.
workspace: /repo
filesystem:
  read_only: [/repo]
  writable: [/repo/src, /repo/tests]
  deny: [/repo/.env]
network:
  default: deny
  allow_hosts: [registry.npmjs.org, pypi.org]
limits:
  runtime_seconds: 120
  processes: 32
approvals:
  required_for: [deploy, git.push, database.delete, email.send]

Allowlist domén není úplná síťová ochrana. Záleží na DNS, proxy, přesměrování, dostupných protokolech i tom, jaká data může nástroj odeslat na povolenou službu. Mounty, credentials, CPU, paměť a procesy mají vlastní omezení. Citlivé soubory hostitele se do prostředí vůbec nemusí dostat.

Schválení musí být navázané na konkrétní payload nebo diff, identitu a platnost. Změní-li se akce po schválení, původní souhlas nestačí. Agent také nemá mít možnost přepsat policy či testovací bránu, podle které se jeho práce posuzuje.

Minimální threat model

  1. Prompt injection: externí dokument, web, issue nebo výsledek nástroje se snaží přepsat zadání. Odděluji data od autority a kontroluji skutečné akce.
  2. Excessive agency: nástroj má větší rozsah, než úloha vyžaduje. Omezuji schopnosti a dobu jejich platnosti.
  3. Tool/MCP poisoning: změna popisu, implementace či odpovědi nástroje ovlivní rozhodování. Verzuji a prověřuji dodavatele i kontrakty.
  4. Memory poisoning: nedůvěryhodný obsah přežije v paměti do další session. Uchovávám provenance a řídím zápis i retrieval.
  5. Improper output handling: aplikace použije vygenerovaný shell, SQL, HTML nebo URL bez běžné validace. Výstup modelu zůstává nedůvěryhodným vstupem.
  6. Supply-chain útoky: skill, plugin nebo extension přináší kód a nové možnosti exekuce. Připínám verze, kontroluji zdroj a oprávnění.
  7. Selhání obnovy a souběhu: dva běhy provedou stejnou akci nebo pracují s jinou revizí. Používám operation IDs, zámky či transakce podle domény.

Pro mapování rizik používám OWASP LLM Top 10, OWASP Agentic Top 10 a MITRE ATLAS. Tyto zdroje jsou rámec pro threat modeling, nikoli certifikát bezpečnosti konkrétní aplikace.

Bezpečnostní test musí zkoušet i chybu policy služby, timeout hooku, podvržený tool result a pokus změnit konfiguraci během běhu. U bezpečnostně kritického rozhodnutí má nedostupná kontrola zabránit provedení, nikoli otevřít alternativní cestu.

Performance tuning podle návratnosti

Nejdříve změřím, kde vzniká čekání a kolik stojí úspěšné dokončení. Pak volím konkrétní zásah:

  1. Stabilní prompt prefix: využít opakované části kontextu tam, kde to provider podporuje.
  2. Context pruning: nahradit přebytečný historický log strukturovaným stavem a relevantními podklady.
  3. Progressive tool disclosure: zpřístupnit aktuálně potřebnou sadu schopností místo stovek schémat.
  4. Paralelizace nezávislých čtení: repozitář, dokumentaci a issue lze často načíst souběžně. Zápisy do sdíleného stavu vyžadují jiný návrh.
  5. Streaming: zkrátit čekání na první užitečnou informaci, i když se celkový compute nezmění.
  6. Model routing: jednoduchou klasifikaci přenechat menšímu modelu, složitou syntézu silnějšímu; routing samostatně evaluovat.
  7. Rozpočty a stop podmínky: zabránit nekonečným smyčkám a opakování stejné chyby.
# Ilustrační limity pro jednu třídu úloh, nikoli univerzální doporučení.

Jak se tento přístup promítá do mé práce

V AgenticDev je těžištěm řízení kontextu, pracovního běhu a auditní stopy. PostHub spojuje kontext jednotlivých značek s asynchronním zpracováním a schvalováním. Zaznamnik.pro propojuje hlasovou interakci s navazujícím backendovým procesem. Každá studie popisuje konkrétní stav a jeho omezení.

Stejný systémový pohled se uplatňuje i mimo LLM: u SCH-EKONOM na rolích a návaznosti pracovních toků, u EPT recepce na cestě od OCR přes potvrzení údajů k evidenci návštěvy. Ne každý problém potřebuje generativní model. Každý potřebuje jasné odpovědnosti, správná data a kontrolovatelný výsledek.

LLM patří dovnitř explicitně stavového runtime s řízenými pravomocemi. Umí navrhnout další krok; systém kolem něj musí zajistit, že je krok přípustný, dohledatelný a vyhodnotitelný. To je pro mě podstata ucelené architektury agentních a LLM systémů.
